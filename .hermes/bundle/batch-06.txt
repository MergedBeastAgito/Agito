//! One skill's record, and one rule it breaks.
//!
//! The record is what a sweep carries: the directory name is the skill's name,
//! because that is the address a reader types and an index cites, and
//! `Directory` is excluded from the digest so the same corpus digests the same
//! in two checkouts.

use serde::{Deserialize, Serialize};

use crate::Struct::Error::Rule;

/// One skill directory, as `discover` reports it.
#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
pub struct Skill {
	/// The directory name, which is the skill's name.
	pub Name:String,
	/// Where the skill lives. Excluded from the digest on purpose.
	pub Directory:String,
	/// The frontmatter's `description`, trimmed; empty when there is none.
	pub Description:String,
	/// The file names directly under `Reference/`, excluding its index, sorted.
	pub References:Vec<String>,
}

/// One rule a skill breaks, as `validate` reports it.
#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
pub struct Finding {
	/// The skill the finding is about.
	pub Skill:String,
	/// Which of the three rules it breaks.
	pub Rule:String,
	/// What was observed, kept apart from the sentence a human reads.
	pub Detail:String,
}

impl Finding {
	/// A finding for one skill, from a rule and what was observed.
	pub fn Of(Skill:&Skill, Rule:Rule, Detail:impl Into<String>) -> Self {
		Self { Skill:Skill.Name.clone(), Rule:Rule.Name().to_string(), Detail:Detail.into() }
	}

	/// The rule this finding reports, if it is one of the three.
	pub fn Code(&self) -> Option<Rule> { Rule::Parse(&self.Rule) }
}

//! The Rust side of the differential run for `agentic.skill.validate`.
//!
//! These cases are not written here: they are read from
//! `scenarios/skill-contract.json`, the same file
//! `Package/skill-contract/Test/Parity.test.ts` reads. What this file adds is
//! only the corpus builder, the interpreter and the assertion - the tree, the
//! steps, the expected result and the expected ordered effect list all come from
//! the scenario file, so the two implementations cannot drift by being tested
//! against two hand-written suites.
//!
//! The capability reads a real filesystem, so the corpus is real: the fixture is
//! materialised under `std::env::temp_dir()` exactly as the TypeScript side
//! materialises it under `mkdtemp`, byte for byte, and removed afterwards. Only
//! the root path differs between the two runs, and the root path is outside every
//! observation - `directory` is excluded from the digest and no effect carries a
//! path.
//!
//! `effects` is what the port reported, in order: every skill a `discover`
//! answered and every finding a `validate` reported. Two ports that answered the
//! same findings in a different order disagree here, which is the whole point.
//!
//! `Test/SkillContract.rs` is kept as it is: that suite is the contract, this one
//! is the comparison. `AGENTIC_PARITY_OUT=<path>` makes this test also write what
//! it observed as JSON, which is how `scenarios/run.mjs --compare` gets the Rust
//! half of the differential run.

#![allow(non_snake_case, non_upper_case_globals)]

use std::{
	collections::BTreeMap,
	fs,
	path::{Path, PathBuf},
	sync::atomic::{AtomicU64, Ordering},
	time::{Duration, SystemTime},
};

use AgenticRuntime::BlockOn;
use AgenticSkillContract::{Create, Skill, SkillContract};
use serde_json::{Map, Value, json};

/// Distinguishes two corpora built in the same process, which one test builds
/// one after another.
static Counter: AtomicU64 = AtomicU64::new(0);

/// A corpus on disk, removed when the case is done with it.
struct Corpus {
	Base: PathBuf,
	Root: PathBuf,
}

impl Drop for Corpus {
	fn drop(&mut self) { let _ = fs::remove_dir_all(&self.Base); }
}

/// One `SKILL.md`, as the contract suite writes it.
fn body(Name: &str, Frontmatter: &str) -> String {
	format!("---\n{Frontmatter}\n---\n\n# {Name}\n\nA body.\n")
}

/// The corpus root's index, from the skills that are cited.
fn index(Names: &[String]) -> String {
	let mut Text = Names
		.iter()
		.map(|Name| format!("- [{Name}/]({Name}/)"))
		.collect::<Vec<String>>()
		.join("\n");
	Text.push('\n');
	Text
}

/// The file a `touchAfterFirstValidate` hook writes, without its extension.
fn stem(Document: &str) -> String {
	let Name = Path::new(Document)
		.file_name()
		.map(|Name| Name.to_string_lossy().into_owned())
		.unwrap_or_default();
	match Name.rsplit_once('.') {
		Some((Left, _)) => Left.to_string(),
		None => Name,
	}
}

fn write(Path: &Path, Text: &str) {
	if let Some(Parent) = Path.parent() {
		fs::create_dir_all(Parent).expect("a directory is writable");
	}
	fs::write(Path, Text).expect("a file is writable");
}

/// Every skill a fixture describes: the corpus, then the one linked in.
fn skills_of(Fixture: &Value) -> Vec<Value> {
	let mut Skills: Vec<Value> = Fixture
		.get("corpus")
		.and_then(Value::as_array)
		.cloned()
		.unwrap_or_default();
	if let Some(Linked) = Fixture.get("symlink").filter(|Value| !Value.is_null()) {
		let mut One = Linked.clone();
		if let Value::Object(Map) = &mut One {
			Map.insert("external".to_string(), Value::Bool(true));
		}
		Skills.push(One);
	}
	Skills
}

/// Build the corpus a fixture describes, and answer it.
///
/// The root sits one directory in from a fresh scratch directory, so the
/// symlinked skill has somewhere to live that is genuinely outside the corpus -
/// a link inside the corpus would prove nothing.
fn materialise(Fixture: &Value) -> Corpus {
	let Unique = format!(
		"skill-parity-{}-{}",
		std::process::id(),
		Counter.fetch_add(1, Ordering::SeqCst)
	);
	let Base = std::env::temp_dir().join(Unique);
	let _ = fs::remove_dir_all(&Base);
	fs::create_dir_all(&Base).expect("the scratch directory is writable");
	let Root = Base.join("corpus");
	let Corpus = Corpus { Base, Root };
	if bool_at(Fixture, &["absentRoot"]).unwrap_or(false) {
		return Corpus;
	}
	let Outside = Corpus.Base.join("outside");
	fs::create_dir_all(&Corpus.Root).expect("the corpus root is writable");
	let mut Cited: Vec<String> = Vec::new();
	for Skill in skills_of(Fixture) {
		let Name = string_at(&Skill, &["name"]).unwrap_or_default();
		let External = bool_at(&Skill, &["external"]).unwrap_or(false);
		let Home = if External { Outside.join(&Name) } else { Corpus.Root.join(&Name) };
		fs::create_dir_all(&Home).expect("the skill directory is writable");
		if !bool_at(&Skill, &["noBody"]).unwrap_or(false) {
			write(
				&Home.join("SKILL.md"),
				&body(&Name, &string_at(&Skill, &["frontmatter"]).unwrap_or_default()),
			);
		}
		if let Some(References) = Skill.get("references").and_then(Value::as_object) {
			for (File, Text) in References {
				write(&Home.join("Reference").join(File), Text.as_str().unwrap_or_default());
			}
		}
		if let Some(Text) = Skill.get("referenceIndex").and_then(Value::as_str) {
			write(&Home.join("Reference").join("Index.md"), Text);
		}
		if External {
			#[cfg(unix)]
			std::os::unix::fs::symlink(&Home, Corpus.Root.join(&Name)).expect("the link is created");
		}
		if bool_at(&Skill, &["cited"]).unwrap_or(true) {
			Cited.push(Name);
		}
	}
	if let Some(Files) = Fixture.get("rootFiles").and_then(Value::as_object) {
		for (File, Text) in Files {
			write(&Corpus.Root.join(File), Text.as_str().unwrap_or_default());
		}
	}
	if let Some(Name) = Fixture.get("corpusIndex").and_then(Value::as_str) {
		write(&Corpus.Root.join(Name), &index(&Cited));
	}
	Corpus
}

/// A day forward, on every file under `Path`.
fn touch(Path: &Path) {
	let Ok(Entries) = fs::read_dir(Path) else {
		return;
	};
	for Entry in Entries.flatten() {
		let Child = Entry.path();
		let Ok(Kind) = Entry.file_type() else {
			continue;
		};
		if Kind.is_dir() {
			touch(&Child);
		} else if Kind.is_file() {
			let Later = SystemTime::now() + Duration::from_secs(86_400);
			if let Ok(File) = fs::OpenOptions::new().write(true).open(&Child) {
				let _ = File.set_times(fs::FileTimes::new().set_modified(Later));
			}
		}
	}
}

/// One record, with the four fields the port promises and nothing else.
fn record(Document: &Value) -> Skill {
	Skill {
		Name: string_at(Document, &["name"]).unwrap_or_default(),
		Directory: string_at(Document, &["directory"]).unwrap_or_default(),
		Description: string_at(Document, &["description"]).unwrap_or_default(),
		References: Document
			.get("references")
			.and_then(Value::as_array)
			.map(|List| List.iter().filter_map(Value::as_str).map(str::to_string).collect())
			.unwrap_or_default(),
	}
}

/// The records a `digest` step hands the port: a literal list, or the last
/// discovered records with one mutation applied.
fn digested(Step: &Value, Held: &[Skill]) -> Vec<Skill> {
	if let Some(List) = Step.get("skills").and_then(Value::as_array) {
		return List.iter().map(record).collect();
	}
	let mut Records = Held.to_vec();
	let Mutate = Step.get("mutate").cloned().unwrap_or(Value::Null);
	if bool_at(&Mutate, &["reverse"]).unwrap_or(false) {
		Records.reverse();
	}
	if let Some(At) = number_at(&Mutate, &["at"]) {
		if let Some(One) = Records.get_mut(At as usize) {
			if let Some(Name) = string_at(&Mutate, &["name"]) {
				One.Name = Name;
			}
			if let Some(Directory) = string_at(&Mutate, &["directory"]) {
				One.Directory = Directory;
			}
			if let Some(Description) = string_at(&Mutate, &["description"]) {
				One.Description = Description;
			}
			if let Some(References) = Mutate.get("references").and_then(Value::as_array) {
				One.References = References.iter().filter_map(Value::as_str).map(str::to_string).collect();
			}
		}
	}
	Records
}

/// Run one scenario, and answer what it did: the result and the ordered effects.
fn run_case(Fixture: &Value, Entry: &Value) -> Value {
	let Fixture = merge(Fixture, Entry.get("fixture").unwrap_or(&Value::Null));
	let Corpus = materialise(&Fixture);
	let Root = Corpus.Root.to_string_lossy().into_owned();
	let Contract = Create();
	let Hook = string_at(&Fixture, &["touchAfterFirstValidate"]);
	let Id = string_at(Entry, &["id"]).unwrap_or_else(|| "<unnamed>".to_string());

	let mut Effects: Vec<String> = Vec::new();
	let mut Held: Vec<Skill> = Vec::new();
	let mut Touched = false;
	let mut Result = Value::Null;

	let Steps = Entry.get("steps").and_then(Value::as_array).cloned().unwrap_or_default();
	for Step in &Steps {
		let Op = string_at(Step, &["op"]).unwrap_or_default();
		match Op.as_str() {
			"discover" => {
				Held = BlockOn(Contract.Discover(&Root));
				for Skill in &Held {
					Effects.push(format!("discovered:{}", Skill.Name));
				}
				Result = json!({
					"kind": "names",
					"names": Held.iter().map(|Skill| Skill.Name.clone()).collect::<Vec<String>>(),
				});
			}
			"touch" => touch(&Corpus.Root),
			"digest" => {
				Result = json!({ "kind": "digest", "value": Contract.Digest(&digested(Step, &Held)) });
			}
			"validate" | "validateDiscovered" => {
				let Wanted = string_at(Step, &["skill"]).unwrap_or_default();
				let One = if Op == "validate" {
					let Discovered = BlockOn(Contract.Discover(&Root));
					for Skill in &Discovered {
						Effects.push(format!("discovered:{}", Skill.Name));
					}
					Discovered.into_iter().find(|Skill| Skill.Name == Wanted)
				} else {
					Held.iter().find(|Skill| Skill.Name == Wanted).cloned()
				};
				let Some(One) = One else {
					panic!("{Id}: no discovered record for {Wanted}");
				};
				let Findings = BlockOn(Contract.Validate(&One));
				for Finding in &Findings {
					Effects.push(format!("finding:{}:{}", Finding.Rule, Finding.Skill));
				}
				Result = json!({
					"kind": "findings",
					"rules": Findings.iter().map(|Finding| Finding.Rule.clone()).collect::<Vec<String>>(),
				});
				if !Touched {
					if let Some(Hook) = &Hook {
						Touched = true;
						write(
							&Path::new(&One.Directory).join(Hook),
							&format!("# {}\n", stem(Hook)),
						);
					}
				}
			}
			Other => panic!("unknown skill step {Other}"),
		}
	}

	json!({ "result": Result, "effects": Effects })
}

/// What one observation got wrong, as sentences. Empty means the case agreed.
///
/// This is `scenarios/lib/load.mjs`'s `compare`, written out for the kinds this
/// capability answers: a `findings` result is compared by rule, a `names` result
/// by the names and their order, and a `digest` result by its exact constant -
/// never by a pattern, because the constant is the evidence.
fn mismatches(Observed: &Value, Expect: &Value) -> Vec<String> {
	let mut Wrong = Vec::new();
	let Want = Expect.get("result").cloned().unwrap_or(Value::Null);
	let Got = Observed.get("result").cloned().unwrap_or(Value::Null);
	let Kind = |Document: &Value| Document.get("kind").and_then(Value::as_str).unwrap_or("").to_string();
	if Kind(&Want) != Kind(&Got) {
		Wrong.push(format!("result kind: wanted {}, got {}", Kind(&Want), Kind(&Got)));
	} else {
		match Kind(&Want).as_str() {
			"findings" => {
				if Want.get("rules") != Got.get("rules") {
					Wrong.push(format!(
						"result rules: wanted {}, got {}",
						Want.get("rules").unwrap_or(&Value::Null),
						Got.get("rules").unwrap_or(&Value::Null)
					));
				}
			}
			"names" => {
				if Want.get("names") != Got.get("names") {
					Wrong.push(format!(
						"result names: wanted {}, got {}",
						Want.get("names").unwrap_or(&Value::Null),
						Got.get("names").unwrap_or(&Value::Null)
					));
				}
			}
			"digest" => {
				if let Some(Equals) = Want.get("equals") {
					if Got.get("value") != Some(Equals) {
						Wrong.push(format!(
							"result digest: wanted {Equals}, got {}",
							Got.get("value").unwrap_or(&Value::Null)
						));
					}
				}
			}
			Other => Wrong.push(format!("unknown result kind {Other}")),
		}
	}
	if let Some(Effects) = Expect.get("effects") {
		if Effects != Observed.get("effects").unwrap_or(&Value::Null) {
			Wrong.push(format!(
				"effects: wanted {Effects}, got {}",
				Observed.get("effects").unwrap_or(&Value::Null)
			));
		}
	}
	Wrong
}

/// Read a dotted path out of a JSON value.
fn at<'a>(Document: &'a Value, Path: &[&str]) -> Option<&'a Value> {
	let mut Cursor = Document;
	for Step in Path {
		Cursor = Cursor.get(*Step)?;
	}
	Some(Cursor)
}

fn string_at(Document: &Value, Path: &[&str]) -> Option<String> {
	at(Document, Path).and_then(Value::as_str).map(str::to_string)
}

fn bool_at(Document: &Value, Path: &[&str]) -> Option<bool> { at(Document, Path).and_then(Value::as_bool) }

fn number_at(Document: &Value, Path: &[&str]) -> Option<u64> { at(Document, Path).and_then(Value::as_u64) }

/// Merge a patch into a fixture, one level deep per section, recursively. A
/// missing patch is not a patch: it leaves the fixture alone.
fn merge(Base: &Value, Patch: &Value) -> Value {
	if Patch.is_null() {
		return Base.clone();
	}
	match (Base, Patch) {
		(Value::Object(Base), Value::Object(Patch)) => {
			let mut Merged = Base.clone();
			for (Key, Patched) in Patch {
				let Next = match Merged.get(Key) {
					Some(Existing) => merge(Existing, Patched),
					None => Patched.clone(),
				};
				Merged.insert(Key.clone(), Next);
			}
			Value::Object(Merged)
		}
		_ => Patch.clone(),
	}
}

/// The scenario file this crate answers to.
fn scenario_file() -> Value {
	let Path = Path::new(env!("CARGO_MANIFEST_DIR")).join("../../scenarios/skill-contract.json");
	let Text = fs::read_to_string(&Path)
		.unwrap_or_else(|Why| panic!("{} is readable: {Why}", Path.display()));
	serde_json::from_str(&Text).unwrap_or_else(|Why| panic!("{} is JSON: {Why}", Path.display()))
}

/// Every case in the file.
fn cases(File: &Value) -> Vec<Value> {
	File.get("cases").and_then(Value::as_array).cloned().unwrap_or_default()
}

/// A case this side cannot express is skipped, and the file says why.
fn skipped_on_rust(Entry: &Value) -> bool {
	Entry
		.get("skip")
		.and_then(Value::as_array)
		.map(|Sides| Sides.iter().any(|Side| Side.as_str() == Some("rust")))
		.unwrap_or(false)
}

/// Every scenario, against its expectation, with what was observed left behind
/// for the differential run to compare against the TypeScript half.
#[test]
fn every_scenario_agrees_with_its_expectation() {
	let File = scenario_file();
	let Fixture = File.get("fixture").cloned().unwrap_or(Value::Null);
	let mut Observed: BTreeMap<String, Value> = BTreeMap::new();
	let mut Wrong: Vec<String> = Vec::new();
	let mut Ran = 0usize;

	for Entry in cases(&File) {
		if skipped_on_rust(&Entry) {
			continue;
		}
		let Id = string_at(&Entry, &["id"]).unwrap_or_else(|| "<unnamed>".to_string());
		let One = run_case(&Fixture, &Entry);
		for Sentence in mismatches(&One, Entry.get("expect").unwrap_or(&Value::Null)) {
			Wrong.push(format!("{Id}: {Sentence}"));
		}
		Observed.insert(Id, One);
		Ran += 1;
	}

	if let Ok(Path) = std::env::var("AGENTIC_PARITY_OUT") {
		let Document =
			serde_json::to_string_pretty(&Value::Object(Observed.clone().into_iter().collect::<Map<String, Value>>()))
				.unwrap_or_default();
		let _ = fs::write(Path, Document);
	}

	assert!(!Observed.is_empty(), "no scenarios were found");
	assert_eq!(
		Ran,
		cases(&File).iter().filter(|Entry| !skipped_on_rust(Entry)).count(),
		"every scenario in the file must run on this side"
	);
	assert!(
		Wrong.is_empty(),
		"the Rust port disagrees with the scenario file:\n{}",
		Wrong.join("\n")
	);
}

/// Every scenario names a case this crate's contract suite has, so the case map
/// in `Documentation/Parity.md` cannot point at a test that was renamed away.
#[test]
fn every_scenario_names_a_case_the_rust_suite_has() {
	let Contract = include_str!("../Test/SkillContract.rs");

		assert!(
			Contract.contains(&format!("fn {Name}(")),

		);
	}
}

//! `agentic.skill.validate`, exercised against corpora this test builds on
//! disk.
//!
//! No network, no browser and no fixture files checked in: a corpus is a
//! temporary directory the test writes, so a test can add a file between two
//! calls and prove that nothing was cached.

use std::{
	fs,
	path::{Path, PathBuf},
};

use AgenticRuntime::BlockOn;
use AgenticSkillContract::{Create, Finding, Rule, Rules, Skill, SkillContract};

/// A fresh, empty corpus root.
fn Root(Tag:&str) -> PathBuf {
	let Base = Path::new(env!("CARGO_TARGET_TMPDIR")).join(Tag);
	let _ = fs::remove_dir_all(&Base);
	fs::create_dir_all(&Base).expect("the corpus root is writable");
	Base
}

/// A skill directory carrying one `SKILL.md`.
fn SkillAt(Root:&Path, Name:&str, Frontmatter:&str) -> PathBuf {
	let Directory = Root.join(Name);
	fs::create_dir_all(&Directory).expect("the skill directory is writable");
	fs::write(Directory.join("SKILL.md"), format!("---\n{Frontmatter}\n---\n\n# {Name}\n"))
		.expect("SKILL.md is writable");
	Directory
}

/// One file under a skill's `Reference/`.
fn ReferenceAt(Directory:&Path, Name:&str, Body:&str) {
	let References = Directory.join("Reference");
	fs::create_dir_all(&References).expect("Reference/ is writable");
	fs::write(References.join(Name), Body).expect("the reference is writable");
}

/// A skill's `Reference/Index.md`.
fn ReferenceIndexAt(Directory:&Path, Body:&str) { ReferenceAt(Directory, "Index.md", Body); }

/// The corpus root's index.
fn CorpusIndexAt(Root:&Path, Name:&str, Body:&str) {
	fs::write(Root.join(Name), Body).expect("the corpus index is writable");
}

fn Discovered(Root:&Path, Name:&str) -> Skill {
	let Skills = BlockOn(Create().Discover(&Root.to_string_lossy()));
	Skills
		.into_iter()
		.find(|Candidate| Candidate.Name == Name)
		.unwrap_or_else(|| panic!("no skill named {Name} was discovered"))
}

fn Findings(Skill:&Skill) -> Vec<Finding> { BlockOn(Create().Validate(Skill)) }

fn RulesOf(Findings:&[Finding]) -> Vec<&str> { Findings.iter().map(|Finding| Finding.Rule.as_str()).collect() }

/// The fixture the recorded digest belongs to.
fn Valid(Root:&Path) -> Skill {
	let Directory = SkillAt(
		Root,
		"Alpha",
		"name: alpha\ndescription: One honest skill, with its reference listed.",
	);
	ReferenceAt(&Directory, "Notes.md", "# Notes\n");
	ReferenceIndexAt(&Directory, "- [Notes.md](Notes.md)\n");
	CorpusIndexAt(Root, "Index.md", "- [Alpha](Alpha/SKILL.md)\n");
	Discovered(Root, "Alpha")
}

#[test]
fn the_port_declares_exactly_the_errors_the_manifest_promises() {
	let Declared:Vec<&str> = Rules.into_iter().map(Rule::Name).collect();
	assert_eq!(Declared, vec!["unparsable", "unlisted-reference", "uncited"]);
	let Manifest = include_str!("../module.json");
	for Name in Declared {
		assert!(Manifest.contains(&format!("\"{Name}\"")), "{Name} is not in module.json");
	}
}

#[test]
fn discover_returns_every_skill_directory_ordered_by_name() {
	let Root = Root("order");
	SkillAt(&Root, "Zulu", "description: Created first, sorted last.");
	SkillAt(&Root, "Alpha", "description: Created second, sorted first.");
	let Names:Vec<String> = BlockOn(Create().Discover(&Root.to_string_lossy()))
		.into_iter()
		.map(|Skill| Skill.Name)
		.collect();
	assert_eq!(Names, vec!["Alpha", "Zulu"]);
}

#[test]
fn discover_is_deterministic_across_two_runs() {
	let Root = Root("deterministic");
	SkillAt(&Root, "Beta", "description: One.");
	SkillAt(&Root, "Alpha", "description: Two.");
	SkillAt(&Root, "Gamma", "description: Three.");

#[cfg(unix)]

//! The one expression that turns a page into measurements.
//!
//! This is a *workflow* decision, not a capability's: the verification package
//! must not know what an element is, so the convention for reading one lives
//! here, where a particular site can replace it.
//!
//! What it reads: `data-value` when the element carries one, parsed as a number
//! when it is numeric, and the element's trimmed text otherwise. A selector
//! that matches nothing is `present: false` with a `null` value, which is the
//! wire shape the capability's port asks for.
//!
//! The JavaScript is `Source/Script/Measure.js`, taken whole. The one value this
//! function supplies - the selector list, already a JSON array - is written where
//! it belongs as `{{selectors}}` and filled at call time, so the file is the
//! expression and this function is only its parameter.

use AgenticRuntime::Fill;
use serde_json::Value;

/// The expression itself.
const MeasureScript:&str = include_str!("../Script/Measure.js");

/// A JavaScript expression that answers one measurement per selector.
pub fn MeasurementExpression(Selectors:&[String]) -> String {
	let Selectors = serde_json::to_string(Selectors).unwrap_or_else(|_| "[]".to_string());
	Fill(MeasureScript, &[("selectors", &Selectors)])
}

/// The selectors a caller asked about, as a JSON array, for a harness that
/// wants to see what was sent without building a page.
pub fn MeasurementSelectors(Expression:&str) -> Option<Value> {
	let Start = Expression.rfind("return ")?;
	let Rest = &Expression[Start + "return ".len()..];
	let End = Rest.find(".map(Read)")?;
	serde_json::from_str(&Rest[..End]).ok()
}

#[cfg(test)]
mod Tests {
	use super::*;
	use AgenticRuntime::Unfilled;

	/// The script is filled completely, the check that says so bites, and what
	/// the expression was built from can still be read back out of it.
	///
	/// The read-back is the part that a rewrite would break silently:
	/// `MeasurementSelectors` finds `return ` and `.map(Read)` in the built
	/// string, so a template that moved either marker would leave every
	/// measurement test passing and every read-back answering `None`.
	#[test]
	fn the_measure_expression_is_filled_and_can_be_read_back() {
		let Selectors = vec!["#main".to_string(), "body > p".to_string()];
		let Built = MeasurementExpression(&Selectors);
		assert_eq!(Unfilled(&Built), None, "the expression still carries a placeholder");
		assert_eq!(Unfilled(MeasureScript).as_deref(), Some("selectors"), "the script carries no placeholder, so nothing proves the fill ran");
		assert_eq!(MeasurementSelectors(&Built), Some(serde_json::json!(["#main", "body > p"])));
	}
}

--- FILE: Crate/Workflow/Source/Fn/VerifySkillPage.rs ---
//! One composition that uses four capabilities in the order a release check
//! does.
//!
//! A corpus is swept, every skill is validated, the corpus is digested, and
//! then a built page is measured and judged. It is written here rather than in
//! a capability because it is the composition that knows all four, and it is
//! written at all because a workflow crate with no workflow in it is a
//! directory.
//!
//! The order is the interesting part: the corpus is read before the page is
//! touched, so a release check that finds a broken skill does not pay for a
//! browser, and a page that cannot be measured does not hide the findings that
//! were already collected.

use AgenticDesignVerification::{Invariant, Measurement, Verdict, Verify};
use AgenticRuntime::{Call, FutureBox};
use AgenticSkillContract::{Finding, Skill, SkillContract};

/// What one release check found.
#[derive(Clone, Debug, Default, PartialEq)]
pub struct Outcome {
	/// Every skill the corpus holds.
	pub Skills:Vec<Skill>,
	/// Every rule a skill broke.
	pub Findings:Vec<Finding>,
	/// The corpus digest, which is stable across checkouts.
	pub Digest:String,
	/// What the page measured, when there was a page to measure.
	pub Measurements:Vec<Measurement>,
	/// The verdict, when there was one.
	pub Verdict:Option<Verdict>,
	/// Why the page could not be measured, when it could not be.
	pub Failure:Option<String>,
}

impl Outcome {
	/// Whether the corpus is clean and the page held.
	pub fn Held(&self) -> bool {
		self.Findings.is_empty() && self.Failure.is_none() && self.Verdict.as_ref().is_none_or(|Verdict| Verdict.Held)
	}
}

/// Sweep a corpus, then measure and judge a page.
pub fn VerifySkillPage<'a>(
	Contract:&'a dyn SkillContract,
	Verify:&'a dyn Verify,
	Root:&'a str,
	Selectors:&'a [String],
	Invariants:&'a [Invariant],
	Call:Call,
) -> FutureBox<'a, Outcome> {
	Box::pin(async move {
		let Skills = Contract.Discover(Root).await;
		let mut Findings = Vec::new();
		for Skill in &Skills {
			Findings.extend(Contract.Validate(Skill).await);
		}
		let Digest = Contract.Digest(&Skills);
		let mut Outcome = Outcome { Skills, Findings, Digest, ..Outcome::default() };

		if Selectors.is_empty() {
			return Outcome;
		}

		match Verify.Measure(Selectors, Call).await {
			Ok(Measurements) => {
				Outcome.Verdict = Some(Verify.Check(Invariants, &Measurements));
				Outcome.Measurements = Measurements;
			},
			Err(Why) => Outcome.Failure = Some(format!("{}: {}", Why.Code().Name(), Why.Message())),
		}
		Outcome
	})
}

--- FILE: Crate/Workflow/Source/Struct/Binding/Measure.rs ---
//! Design verification's `Browse`, over the browser substrate.
//!
//! The capability's port has one verb and no session, so this binding opens the
//! configured page for each measurement and releases it afterwards. That is not
//! an oversight: the manifest says `stateless`, and a binding that kept a page
//! alive between measurements would turn a stateless capability into a
//! `holds-transport` one behind its own manifest.
//!
//! The expression this binding sends is the one place a page convention lives,
//! and it is deliberately in the workflow rather than in the verification
//! package: the package must not know what an element is, and a workflow is
//! exactly the layer that decides how a particular site is read.

use std::sync::Arc;

use AgenticBrowserCDP::{Browse as BrowserBrowse, Error as BrowserError, OpenOptions};
use AgenticDesignVerification::{Browse, Failure};
use AgenticRuntime::{Call, FutureBox};
use serde_json::Value;

use crate::Fn::Measure::MeasurementExpression;

/// The verification capability's transport, served by the browser substrate.
pub struct Measure {
	Browse:Arc<dyn BrowserBrowse>,
	Url:String,
}

/// Bind design verification's `Browse` to one page of one browser.
pub fn Create(Browse:Arc<dyn BrowserBrowse>, Url:impl Into<String>) -> Measure { Measure { Browse, Url:Url.into() } }

/// A browser failure, said in the verification port's vocabulary.
fn Classify(Why:BrowserError) -> Failure {
	Failure {
		Message:format!("{}: {}", Why.Code().Name(), Why.Message()),
		Detail:Why.Detail().to_string(),
	}
}

impl Browse for Measure {
	fn Measure<'a>(&'a self, Selectors:&'a [String], Call:Call) -> FutureBox<'a, Result<Vec<Value>, Failure>> {
		Box::pin(async move {
			let Target = self
				.Browse
				.Open(&self.Url, OpenOptions::Launch(Call.clone()))
				.await
				.map_err(Classify)?;
			let Expression = MeasurementExpression(Selectors);
			let Read = self.Browse.Evaluate(&Target, &Expression, Call).await;
			// Released on every path: the capability is stateless, so the page
			// must not outlive the measurement that asked for it.
			self.Browse.Dispose(Target).await;
			match Read {
				Ok(Value::Array(Entries)) => Ok(Entries),
				Ok(Other) => {
					Err(Failure::Of(format!(
						"the page answered {Other} instead of a list of measurements"
					)))
				},
				Err(Why) => Err(Classify(Why)),
			}
		})
	}
}

--- FILE: Crate/Workflow/Source/Struct/Binding/Page.rs ---
//! The chat driver's `Page`, over the browser substrate.
//!
//! Three translations, and each one is a decision this layer owns:
//!
//! 1. **Ownership.** `Page` has no ownership because a chat driver must not
//!    care whether the browser was launched or attached. This binding launches,
//!    because a capability that asks a product a question owns the page it
//!    opened; a caller that wants a shared browser supplies a `Browse` that
//!    attaches instead.
//! 2. **The handle.** The driver passes back whatever `Open` returned and never
//!    reads it, so the browser target lives here, keyed by the URL the driver
//!    does keep. That is the whole of "a provider may hang whatever it needs
//!    there".
//! 3. **The vocabulary.** A browser failure has three codes and the chat port
//!    has four; the browser's code and message travel in the failure's
//!    `message`, and its observation in `detail`, so the driver can map the
//!    whole thing onto `not-ready` without losing which of the three happened.

use std::{
	collections::HashMap,
	sync::{Arc, Mutex, MutexGuard},
};

use AgenticBrowserCDP::{Browse as BrowserBrowse, Error as BrowserError, OpenOptions, Target as BrowserTarget};
use AgenticChatDriver::{Failure, Page as ChatPage, Target};
use AgenticRuntime::{Call, FutureBox};
use serde_json::Value;

/// The chat driver's page, served by the browser substrate.
pub struct Page {
	Browse:Arc<dyn BrowserBrowse>,
	/// Where to attach, when the caller wants a browser it did not start.
	Attach:Option<String>,
	/// Which page to bind on that browser, when it is not a new one.
	Bind:Option<String>,
	/// What each chat target was bound to, by URL.
	Held:Mutex<HashMap<String, BrowserTarget>>,
}

/// Bind the chat driver's `Page` to a browser this session launches.
pub fn Create(Browse:Arc<dyn BrowserBrowse>) -> Page {
	Page { Browse, Attach:None, Bind:None, Held:Mutex::new(HashMap::new()) }
}

/// Bind the chat driver's `Page` to a browser somebody else owns, and to the
/// page `Bind` names when it is given.
///
/// Attaching without a bind opens a page in that browser; attaching with one
/// drives the page that is already there, which is the difference between a
/// test run and a conversation with a tab a person is looking at.
pub fn Attached(Browse:Arc<dyn BrowserBrowse>, Endpoint:impl Into<String>, Bind:Option<String>) -> Page {
	Page { Browse, Attach:Some(Endpoint.into()), Bind, Held:Mutex::new(HashMap::new()) }
}

impl Page {
	fn Lock(&self) -> MutexGuard<'_, HashMap<String, BrowserTarget>> {
		self.Held.lock().unwrap_or_else(|Poison| Poison.into_inner())
	}
}

/// A browser failure, said in the chat port's vocabulary.
///
/// The code is kept: a consumer reading `detail` can still tell an unavailable
/// browser from a page that failed to load, which is the difference between
/// retrying and fixing the page.
fn Classify(Why:BrowserError) -> Failure {
	Failure {
		Message:format!("{}: {}", Why.Code().Name(), Why.Message()),
		Detail:Why.Detail().to_string(),
	}
}

impl ChatPage for Page {
	fn Open<'a>(&'a self, Url:&'a str, Call:Call) -> FutureBox<'a, Result<Target, Failure>> {
		Box::pin(async move {
			let Options = match (&self.Attach, &self.Bind) {
				(Some(Endpoint), Some(Key)) => OpenOptions::Existing(Endpoint.clone(), Key.clone(), Call),
				(Some(Endpoint), None) => OpenOptions::Attach(Endpoint.clone(), Call),
				(None, _) => OpenOptions::Launch(Call),
			};
			let Target = self.Browse.Open(Url, Options).await.map_err(Classify)?;
			self.Lock().insert(Target.Url.clone(), Target.clone());
			Ok(Target { Url:Target.Url })
		})
	}

	fn Evaluate<'a>(
		&'a self,
		Target:&'a Target,
		Expression:&'a str,
		Call:Call,
	) -> FutureBox<'a, Result<Value, Failure>> {
		Box::pin(async move {
			let Held = self.Lock().get(&Target.Url).cloned();
			let Some(Held) = Held else {
				return Err(Failure::Of("this binding holds no browser target for the page"));
			};
			self.Browse.Evaluate(&Held, Expression, Call).await.map_err(Classify)
		})
	}

	fn Dispose<'a>(&'a self, Target:Target) -> FutureBox<'a, ()> {
		Box::pin(async move {
			let Held = self.Lock().remove(&Target.Url);
			if let Some(Held) = Held {
				self.Browse.Dispose(Held).await;
			}
		})
	}
}

fn Span(Milliseconds:u64) -> Duration { Duration::from_millis(Milliseconds) }

/// A clock the test owns.
struct TestPace {
	Now:Mutex<Instant>,
}

impl TestPace {
	fn New() -> Arc<Self> { Arc::new(Self { Now:Mutex::new(Instant::now()) }) }
}

impl Clock for TestPace {
	fn Now(&self) -> Instant { *self.Now.lock().unwrap() }
}

impl Pace for TestPace {
	fn Sleep(&self, Span:Duration) -> FutureBox<'_, ()> {
		*self.Now.lock().unwrap() += Span.max(Duration::from_millis(1));
		Box::pin(std::future::ready(()))
	}
}

/// A browser that answers the expression it is handed.
struct FakeBrowse {
	Answer:Mutex<Result<Value, BrowserError>>,
	Opens:AtomicU64,
	Disposes:AtomicU64,
	Expressions:Mutex<Vec<String>>,
}

impl FakeBrowse {
	fn Answering(Value:Value) -> Arc<Self> {
		Arc::new(Self {
			Answer:Mutex::new(Ok(Value)),
			Opens:AtomicU64::new(0),
			Disposes:AtomicU64::new(0),
			Expressions:Mutex::new(Vec::new()),
		})
	}

	fn Failing(Why:BrowserError) -> Arc<Self> {
		Arc::new(Self {
			Answer:Mutex::new(Err(Why)),
			Opens:AtomicU64::new(0),
			Disposes:AtomicU64::new(0),
			Expressions:Mutex::new(Vec::new()),
		})
	}
}

impl BrowserBrowse for FakeBrowse {
	fn Open<'a>(&'a self, Url:&'a str, _Options:OpenOptions) -> FutureBox<'a, Result<Target, BrowserError>> {
		self.Opens.fetch_add(1, Ordering::SeqCst);
		let Answer = self.Answer.lock().unwrap().clone();
		Box::pin(async move {
			// A fake that is scripted to fail fails everywhere, so a test can
			// say "this browser is unreachable" once and mean it.
			if let Err(Why) = Answer {
				return Err(Why);
			}
			Ok(Target {
				Url:Url.to_string(),
				Ws:"ws://fake".to_string(),
				Ownership:AgenticBrowserCDP::Ownership::Launched,
			})
		})
	}

	fn Evaluate<'a>(
		&'a self,
		_Target:&'a Target,
		Expression:&'a str,
		_Call:Call,
	) -> FutureBox<'a, Result<Value, BrowserError>> {
		self.Expressions.lock().unwrap().push(Expression.to_string());
		let Answer = self.Answer.lock().unwrap().clone();
		Box::pin(async move { Answer })
	}

	fn Dispose<'a>(&'a self, _Target:Target) -> FutureBox<'a, ()> {
		self.Disposes.fetch_add(1, Ordering::SeqCst);
		Box::pin(async move {})
	}
}

fn Call(Pace:&TestPace) -> Call { Call::Within(Span(2_000), Pace, Arc::new(Never)) }

# Design

What this workspace is for, and the decisions that shape it. Written after a research pass over the
real inventory of the consuming repository, so the boundaries here are argued from that surface
rather than from a taxonomy.

Provenance convention: each section below opens with **Source:** naming the capture in
`.hermes/research/` that states the claim, or **Decision: this repository** where no capture does.
`Documentation/Research.md` indexes the captures.

## The problem

**Decision: this repository** - the 125 module / 13 skill / 17 script inventory, and the four
capabilities it implies, are measurements of the consuming repository. No capture records them.
`delo-e9b61659.md` is a research pass over one subsystem of that repository, which supports the
premise in the opening paragraph rather than the numbers.

A repository of 125 TypeScript modules, 13 documentation skills and 17 reference scripts has
capabilities that are useful outside it - browser control, chat research, design measurement, skill
validation - but each is entangled with the product it was written for. The goal is to lift those
capabilities out without lifting the product with them.

## The four layers

**Source:** `.hermes/research/rust-4ffde6d5.md` - the layer table, "the arrows point inward", "a
capability importing an adapter is a defect" and "ports are owned by their consumers, not by a
central crate" are stated there, and §1 answers the Cargo consequence: no shared ports crate, two
consumer-owned `Browse` traits. **Decision: this repository** - the reason given for the defect (a
capability untestable without its provider) and the rule that a shared contract is extracted only
when two consumers genuinely share semantics and evolution policy.

| Layer            | Owns                                       | May import                   |
| ---------------- | ------------------------------------------ | ---------------------------- |
| Capability       | a use case and the port it needs           | its own port and data shapes |
| Adapter          | one port against one mechanism or provider | that port, that provider     |
| Workflow         | a composition of capabilities              | capabilities only            |
| Composition root | the binding of ports to adapters           | everything                   |

The arrows point inward. Nothing imports a root, and a capability that imports an adapter is a
defect: it makes the capability untestable without the provider, which is the property this
workspace exists to keep.

**Ports belong to their consumers, not to a centre.** A shared ports package becomes the dependency
magnet at forty modules - one workflow's requirement then forces edits through unrelated modules.
Extract a shared contract only when two consumers genuinely share semantics and evolution policy.

**A port states more than data shapes.** Domain errors, ordering, pagination, cancellation,
idempotency, consistency and resource ownership belong in the port, or two adapters type-check and
still behave differently.

## The manifest

**Source:** `.hermes/research/rust-4ffde6d5.md` - the four state classes and their admission role,
the hashed `artefact` entry point and the cold/warm `cost` are stated there, and §3 answers how they
survive into Rust: a checked-in `module.json`, serde validation in CI, read by a harness that never
starts the application. **Decision: this repository** - the observation each class implies: a
liveness probe for `holds-transport`, a freshness check for `holds-identity`, a reset proof for
`holds-workspace`. The capture says what a harness must revalidate at admission, not which
observation proves it.

Every package carries `module.json`. The field that does the most work is `state`:

- `stateless` - nothing to check at admission.
- `holds-transport` - a liveness probe, because an open socket can be dead.
- `holds-identity` - a freshness check, because a token expires while pooled.
- `holds-workspace` - a reset proof, because a dirty workspace answers wrongly.

`artefact` carries a hashed entry point, so a harness loads a built file and never builds at launch.
`cost` carries cold and warm figures, so a pre-warm planner has something to budget against rather
than guessing.

## The lifecycle

**Decision: this repository** - the seven-step order, and the claim that preparation and admission
are different acts. The captures supply the vocabulary (admission, leases, budgets, cancellation,
cleanup) but not this sequence. `delo-e9b61659.md` supplies the failure the paragraph below is
about: a completed click accepted as a write, and an article's existence accepted as readiness
(`:40-54`, `:96-116`).

prepare reusable infrastructure → lease an isolated context → bind identity and task → validate
credentials, connections and versions → execute within a fresh budget → persist only authorised
artefacts → destroy or prove a reset.

Preparation improves latency. Admission establishes correctness. Merging them is how a warm pool
starts returning wrong answers quickly.

## Why the packages are these five

**Source:** `.hermes/research/rust-4ffde6d5.md` - the five packages with their kinds, state classes
and errors, and §1's decision that all five stay separate crates rather than becoming modules of
one. **Decision: this repository** - the build order, and each reason for building that package when
it is built. The capture says which crates exist, not which one to write first.

Chosen in build order, each justified by a consumer that already exists:

1. **browser-cdp** - the only execution substrate shared by chat research, design verification,
   scraping and browser maintenance. Build it first because everything else needs it.
2. **chat-driver** - a real reusable behaviour with identifiable failure semantics: turn
   correlation, mode and model verification, completion deadlines, trace extraction.
3. **design-verification** - separates a measurement engine from the particular design being
   measured.
4. **skill-contract** - gives a large skill corpus one validation path without pretending every
   skill is executable infrastructure.
5. **runtime** - admission, leases, budgets, cancellation, cleanup. Build it last, after the four
   above expose real lifecycle needs; otherwise it is a harness designed around imagined
   commonality.

## What is deliberately not here

**Decision: this repository** - the exclusion list. No capture discusses store, model, command,
vote, ingest, board synchronisation or gateway maintenance as a capability domain; the words appear
only in other senses (a probabilistic model, a cost model, a CLI command).

Domain policy and write authority stay with their consumers until a second workflow demonstrates a
stable contract: store, model, command, vote, ingest, board synchronisation, gateway maintenance. A
generic name is not a port, and a package called `model` or `context` becomes foundational by
default unless somebody refuses it.

## The two failures this design expects

**Source:** `.hermes/research/rust-4ffde6d5.md` §2 for the ownership half -
`Ownership::{Attached, Launched}`, attach and launch as separate operations, disposal of an attached
session that must not terminate the browser, and a disconnected session that invalidates warm
readiness. **Decision: this repository** - the five-surface inventory, the global warm browser
scenario, and the extraction failure. No capture examines either.

**Competing browser owners.** Five surfaces already touch browser execution with different ownership
needs - a driver, a verifier, a scraper, a relaunch tool, an audit. A global warm browser can close
a session someone else owns, reuse the wrong account, or couple an isolated audit to interactive
state. The lease model has to make ownership explicit before any of it is shared.

**Source-relative assumptions surviving extraction.** Bundling into `Target/` does not make
`Reference/`, routes, tokens, configuration or sibling paths portable. The test is installing packed
artefacts into a fixture with the original repository unavailable.

## The warning metric

**Decision: this repository** - the metric itself. Unrelated coordination per change is this
document's proposal; nothing in the captures measures it or names it.

After two years the bad version of this design has hundreds of package files, duplicated manifests,
permissive graph exceptions, warm contexts nobody can safely evict, and consumers pinned to matching
release trains. The useful signal is not package count: it is **unrelated coordination per
change** - how many packages must be edited together for one workflow's requirement.

# Diagrams

One folder per category. Each folder holds a page, the `.mmd` source of every diagram on that page,
and the `.svg` rendered from that source - so the set reads without the CLI, and a change is made in
a file that renders the same way twice.

A page is a storyboard: pages separated by a rule, the first page what exists, the last page the
states nobody has built. That is deliberate - a diagram that shows only what exists is a
description, and the useful part of a diagram is the gap between it and the goal.

## The convention

A diagram is a `.mmd` file with frontmatter and typed nodes:

```mmd
---
title: <what this diagram shows>
line9:
  theme: boardroom
---
flowchart LR
  A["a runtime surface"]:::host
  B[("persisted state")]:::store
  C["a refusal"]:::fail
  A ==> B
  B -.-> C
```

`line9 render <file>.mmd --out <file>.svg` writes the sibling. It serves flowcharts only: a valid
`stateDiagram-v2` or `sequenceDiagram` exits `9` and writes nothing, so those stay fenced blocks in
the page, with a sentence saying why.

The legend is four class annotations and nothing else - no `note`, no subgraph of prose inside a
drawing:

| Annotation | Means                                          | Shape                       |
| ---------- | ---------------------------------------------- | --------------------------- |
| `:::host`  | an existing runtime surface                    | `["…"]`, `(["…"])` an event |
| `:::hook`  | an installable step, including a missing state | `["…"]`                     |
| `:::store` | persisted state                                | `[("…")]`                   |
| `:::fail`  | an error or refusal                            | `["…"]`                     |

Shapes carry kind: `(["event"])`, `[("store")]`, `{"decision"}`, `["process"]`. Arrows are graded:
`==>` primary, `-->` secondary, `-.->` optional. Line breaks are `<br>`.

# Observability: the database is the surface

An earlier pass argued that SpacetimeDB is a poor fit for control flow and that orchestration
belongs in Rust. That was too broad, and this document records the correction because it changes the
architecture.

## The rule, as a decision procedure

For any new piece of behaviour, ask one question: **does it touch the outside world?**

- Pushing JavaScript into a page, opening a socket, spawning a process, reading a file, waiting on a
  network reply - that is an effect, and it lives in Rust, in a crate that owns the transport.
- Everything that is a decision, a counter, a phase, a retry, a budget, a lease, a claim, a
  cancellation request, an operator command, or a record of any of those - that is an internality,
  and it lives in a table, changed by a reducer.

The test is not "is it important" or "is it fast". It is whether the thing has an observable effect
outside the database. A retry count is internal. The HTTP call it guards is external. A "we are now
on phase three" is internal. The DOM evaluation that phase three performs is external.

When a piece of work straddles the line - a scrape is a decision plus a page read plus a write -
split it: the reducer moves the phase and grants the lease, the Rust effect runner performs the
read, and a second reducer records the result. Two transactions, one truth, and the gap between them
is visible as a lease that is held.

## The corrected boundary

The line is not control flow versus data. It is **effects versus state**.

| Lives in SpacetimeDB                | Lives in Rust                          |
| ----------------------------------- | -------------------------------------- |
| workflow transitions between phases | the browser connection and its socket  |
| admission decisions                 | DOM evaluation and input dispatch      |
| leases, fences, expiry              | process and filesystem operations      |
| budgets and their consumption       | the work an effect actually performs   |
| cancellation requests               | honouring a cancellation mid-operation |
| operator commands                   | the binary's own supervision           |

Rust does not need a second authoritative workflow engine whose decisions are copied into the
database afterwards. That copy is a second state machine, and the reconciliation between the two is
the bug you spend the next year fixing.

## Why a reducer is the right primitive

A reducer is one transaction. That means a single call can:

1. move an invocation into a new phase,
2. reserve its budget,
3. grant its resource lease,
4. record the transition and its cause,
5. and make the resulting state visible to every subscriber,

and if any step fails, none of it happened. A log line cannot do the fourth step, and an out-of-band
write cannot do the fifth. This is the difference between a dashboard that describes the system and
a dashboard that _is_ the system's state.

## What this buys over OTEL

- **Subscriptions are a live view, not a query loop.** A panel sees a change because it was pushed,
  not because it polled.
- **The record and the state are the same bytes.** There is no window in which the trace says one
  thing and the state another.
- **Replay is re-reading.** A generation's rows are what happened; a subscription replayed from the
  start is the history.
- **Atomicity is the transaction, not a convention.** A partial transition is not a thing that can
  be recorded.

## What OTEL still does better

- **Cross-process and cross-vendor traces.** A database only observes what writes to it; a process
  that dies before its first write leaves no row. OTEL's collector sees the process, the crash and
  the resource pressure around it.
- **Cardinality at volume.** Metrics with unbounded label sets are cheap to emit and expensive to
  store as rows.
- **Ecosystem.** Existing dashboards, alerting and retention policies.

The honest position: SpacetimeDB for the state machine and the operational surface; OTEL for what
happens _around_ the process, if it is wanted at all.

## The dashboard

One surface, exported from inside the binary, able to attach to any deployment:

- **Transport**: a subscription over the same database the workers write to. Not a second API,
  because a second API is a second truth.
- **Identity**: the panel connects as a client with its own identity and a role that grants read on
  the operational tables and no write. The role is data, so it can be revoked without a redeploy.
- **Federation**, in ascending order of effort: one shared control database for every enrolled
  binary; several panel connections each labelled with its environment; or a designed replication
  layer. SpacetimeDB's inter-database communication is outbox-based - a message row delivered as a
  reducer call - which is evidence for that pattern, not proof of global transactions across
  databases.
- **Staleness is visible.** A disconnected panel or a worker whose heartbeat has expired must render
  as unknown, never as healthy-because-of-its-last-row. The cheapest way to guarantee that is a
  heartbeat table plus a view that computes freshness from the database's own clock.

## What this rules out

- A second scheduler in Rust that decides what the database then records.
- A dashboard that polls a REST projection of the tables.
- Any state that exists only in a process and is "synced later".

# Thread 1 - hidden properties and disclosure

Source: `.hermes/research/research-575cb198.md`. Nothing in this workspace talks to SpacetimeDB yet,
so every experiment below is a probe against a local instance rather than a test in this tree.
`spacetime sql <database> "<query>"` is the shape of the check; `<database>` has to exist first.

## Q1 - What does a failed transaction roll back?

**Asked:** the thread's follow-up list (`research-575cb198.md:145`).

**Settle it with:** a reducer that inserts a row, then panics; query the table afterwards. A
surviving row means the insert is not part of the rollback.

```sh
spacetime sql < database > "SELECT * FROM Observation"
```

Repeat with a reducer that schedules a reducer and then fails - whether the schedule survives is a
separate answer.

**Blocks:** the `observe()` rule of charging and revealing in one transaction (`:135`). If rollback
is partial, "pay and reveal is all-or-nothing" is false and the reducer has to be restructured.

## Q2 - What is the exact concurrency model across modules?

**Asked:** the thread's follow-up list (`:146`).

**Settle it with:** two reducers in two different databases, each recording a start and end
timestamp; run them concurrently and read the interleaving. Then repeat inside one database, where
the thread says execution is serial (`:11`).

**Blocks:** the nonleakage argument, which assumes an observer cannot learn from interleaving it did
not cause.

## Q3 - How are scheduled reducers sequenced internally?

**Asked:** the thread's follow-up list (`:147`).

**Settle it with:** schedule two reducers for the same timestamp and record invocation order across
repeated runs. The thread already warns that no dispatch order is guaranteed (`:14`), so the
experiment's job is to find out whether that is merely undocumented or actually unstable.

**Blocks:** any probe-expiry or budget-refill design, both of which want a deterministic clock.

## Q4 - What are the formal guarantees of client subscriptions?

**Asked:** the thread's follow-up list (`:148`).

**Settle it with:** two clients, identities A and B, each subscribing to every public table and
every view, ignoring the intended UI; then compare the two transcripts field by field (`:127`,
`:132`).

**Blocks:** the nonleakage target itself (`:140`). A guarantee of "same visible values" is weaker
than the transcript equality the thread specifies, and only a subscription guarantee can close the
difference.

## Q5 - How does state replication affect determinism?

**Asked:** the thread's follow-up list (`:149`).

**Settle it with:** two replicas fed the same transaction stream; compare the observable transcripts
they serve. Divergence means the paired-world test cannot be run against a single node and
generalised.

**Blocks:** the paired-world experiment below (Q8), and with it the whole formal leakage claim.

## Q6 - Does one probe action strictly dominate all the others?

**Asked:** the thread's own check (`:122`).

**Settle it with:** enumerate the legal probes for one capability, compute what each reveals per
unit of cost, and check whether one action is weakly better in every belief state. If it is, the
hidden-information mechanic is degenerate and the disclosure policy has failed its own fairness
test.

**Blocks:** the disclosure policy. A policy that permits a dominant probe has published the secret
with extra steps.

## Q7 - Can two racing probes exceed a one-use allowance?

**Asked:** the thread's own check (`:135`).

**Settle it with:** two clients probing a capability with an allowance of one, in the same
transaction window; count the `Observation` rows written. The reducer authenticates and charges
before revealing, so the count must be one.

**Blocks:** the `observe()` reducer contract. This is the only place where the thread claims
atomicity buys correctness, so it is the one that has to be run.

## Q8 - Does a planted secret canary appear anywhere a client can see?

**Asked:** the thread's own check (`:139`).

**Settle it with:** plant a canary value in a private property, run a full probe, then read every
client-visible row, trace, failure response, result-size field and exported artefact, and grep for
the canary. Then run the paired worlds of `:140` - two databases differing only in the secret - and
diff the complete observable transcripts.

**Blocks:** the trace-projection rule and the claim that the schema provides nonleakage. The thread
is explicit that timing, size, contention and operator access are outside it (`:141`); the
experiment's job is to show those are the _only_ channels left.

# What blocks the most work

**Q18, Rust/TypeScript parity.** Everything in `Documentation/Rust.md` past the crate layout waits
on it, and the thread's own recommendation is conditional on it. A failed parity run does not
invalidate the port; it converts the sidecar from migration bridge to permanent component, which
changes the crate count.

**Q19 and Q20, manifest mapping and the arrows check.** These are the two halves of the answer that
was cut off. Without them the manifest is a JSON file nobody has mapped and the layering rule is a
convention, which is exactly the state the Rust port exists to leave behind.

**Q9 and Q10, transport identity.** If a transport can address a post by position, the browser
port's signature is wrong, and it is wrong in a way that every capability above it inherits. This is
the cheapest of the blocking questions to settle - a fixture page and no live account - which makes

# Parity

What this file claims, and what it does not.

Seventy-five green assertions establish that seventy-five assertions passed. They do not establish
that the Rust port and the TypeScript one are the same program. This file is the evidence that they
are: one scenario file per capability that both implementations read, the ordered effects each one
produced, a mutation suite that proves the assertions bite, and a map from every TypeScript case to
its Rust counterpart.

The claim is narrow on purpose. It is not that the Rust port is correct, and not that the scenario
files cover the whole of either implementation. It is that for the behaviours both suites already
assert, both implementations produce the same result **and** the same ordered sequence of externally
visible effects when driven by the same input.

---

## The shape of the differential run

- **One file per capability is the input.** `scenarios/browser-cdp.json`,
  `scenarios/chat-driver.json` and `scenarios/skill-contract.json` describe a fixture, a sequence of
  operations, and the expected result. Nothing about a case lives in either language's test file:
  the TypeScript side (`scenarios/lib/*.mjs`, driven by `Package/*/Test/Parity.test.ts`) and the
  Rust side (`Crate/*/Test/Parity.rs`) both read the same JSON and answer the same `expect`
  block, so the two suites cannot drift by being written twice.

- **Effects are the protocol, not the result.** Every fixture records what the implementation did to
  it, in order: `launch:`, `attach:`, `handed:`, `evaluate:`, `close:`, `detach:`, `report:` for the
  browser; `open:`, `opened:`, `evaluate:<kind>`, `written:`, `sent:`, `refused:submit:disabled`,
  `release:`, `report:` for the chat page; `discovered:` and `finding:` for a corpus. Equality is
  asserted on that list as well as on the return value, so an implementation that answers correctly
  by the wrong route fails. Two of the five mutations are caught by nothing else: the order of
  `evaluate:model` against `evaluate:submit`, and the number of `evaluate:answers` reads.

- **Timing cases are generated.** `scenarios/generate.mjs` produces
  `scenarios/generated/browser-cdp.timing.json` and `scenarios/generated/chat-driver.timing.json`
  from a (phase × event) matrix - cancellation mid-operation, deadline expiry, transport death
  mid-operation, the three-read stability threshold, a hung release - and each case carries the
  parameters that produced it. The files are committed so both sides can read them, and `run.mjs`
  refuses to compare against a copy that no longer matches the generator.

- **The referee is one script.** `node scenarios/run.mjs --compare` runs the TypeScript half
  in-process, asks cargo for the Rust half through `AGENTIC_PARITY_OUT`, and reports per scenario.
  `node scenarios/mutate.mjs --check` applies five deliberate defects to the real sources, one at a
  time, and insists both suites reject each one.

```
node scenarios/run.mjs --compare        # 82 scenarios, both implementations
node scenarios/mutate.mjs --check       # five mutations, both suites must fail
cargo test --workspace                  # the Rust suite, including Test/Parity.rs
cd Package/browser-cdp && node --test Test/*.test.ts   # and the other two packages
```

- **What the run reported.** 82 scenarios exist across the three capabilities; 79 agreed on both
  sides, 3 are unported (below), 0 differed. The Rust halves are 23 browse scenarios, 29 chat
  scenarios and 26 skill scenarios; the difference between those numbers and 82 is the browse case
  whose release cannot fail in Rust, and the three chat cases neither side can express.

## The three unported cases

Each of these has no Rust counterpart of any kind - not a unit case, not a scenario - and the reason
is a fact about the two type systems rather than about the two behaviours.

- **`resolves even when handed something that is not a target`** (row 25). The TypeScript case calls
  `dispose(undefined)` and asserts the port reports it rather than throwing, because a caller is not
  a type checker. Rust's `Dispose` takes a `Target` by value: there is no value that is not a
  target, so there is no hole to fall into and nothing to prove. The rule it protects - dispose
  never fails - is covered in Rust by `resolves_even_when_handed_a_target_with_no_endpoint` and by
  the scenario `dispose-foreign-target`.

- **`refuses a call with no options as not-ready, not a TypeError`** (row 52). Same hole:
  `undefined` where an `OperationOptions` is declared. In Rust a `Call` is a value the caller must
  construct, and the deadline and cancellation are fields of it.

- **`refuses a call with no question as not-ready, not a TypeError`** (row 53). Same hole again: a
  missing `Question`. Rust's `Question` is a struct with no absent value.

Two further cases have no executed scenario but are not unported, and are worth naming so the count
is not mysterious:

- **Row 1 and row 27** (`the port declares exactly the errors the manifest promises`) assert that a
  package's `module.json` names the same codes its type declares. There is no operation to drive and
  no page to open, so no scenario can express it; both suites keep the assertion in their own files.

- **Row 21** (`reports a failing release instead of throwing it`) runs as a scenario on the
  TypeScript side only. Rust's `Transport::Close` returns `()`, so a release cannot fail and there
  is no cause to report - only a hang is reportable, which is `generated/dispose-hang`. The Rust
  unit case `reports_a_failing_release_instead_of_returning_it` models the same rule with a hung
  release, which is the only shape the Rust port has for it.

- **Rows 39 and 42** (`does not wait for ever on a page that ignores its deadline` /
  `... never opens`) run as scenarios on both sides but have no Rust unit case: `Test/Chat.rs` has
  no hanging page. The parity fake does, so the rule is proved for the Rust port by the differential
  run and not by its own suite. That is a gap in `Test/Chat.rs`, not in the port.

One more thing the table does not say: eight skill-contract cases assert on the _text_ of a
finding's detail as well as on its rule. The scenario compares findings by rule only, because an
`unparsable` detail embeds the absolute skill directory and necessarily differs between two runs in
two temporary directories. Detail wording is compared by the two contract suites, which build their
corpora in process.

## Where the two ports differ today, and why the scenarios tolerate it

These are real differences, recorded rather than smoothed over. None of them changes a code, an
effect, or a report count - which is why the differential run is green - but a reader comparing the
two sources would find them.

- **The sentence and the observation are split differently.** TypeScript writes its own sentence and
  keeps the reason in `detail`; the Rust port has one error type with `Message` and `Detail` and
  reaches for whichever it has. `open-unavailable` therefore asserts that the token `ECONNREFUSED`
  survives somewhere in the failure, not which field it sits in.

- **Deadline wording.** TypeScript's message carries the budget that was left when the read started
  (`answer exceeded its 38ms deadline`); Rust's carries the whole budget
  (`answer exceeded the 40ms deadline`). The code and `detail` are identical, so the scenarios
  assert those.

- **Rust's open timeout loses the word "deadline".** TypeScript says
  `open exceeded its 60ms deadline`; Rust says `the chat page could not be opened` and puts
  `the page never answered` in `detail`. The scenario `open-hangs` asserts the code and the
  observation. This is a defect in the Rust port's wording, not in its behaviour.

- **`Names` disagrees on a non-ASCII boundary.** TypeScript's `Names` spells the boundary as a
  negated character class over word characters, dots and hyphens - and JavaScript's `\w` is ASCII,
  so `é` ends a name; the Rust port uses `char::is_alphanumeric`, which is Unicode, so `é` continues
  one. With `Reference/Notes.md` on disk and `Reference/Index.md` containing `caféNotes.md`, the
  TypeScript port answers no findings and the Rust port answers `unlisted-reference`. No scenario
  covers it, because it would fail on one side; every ASCII case in the file agrees. The fix belongs
  in one of the two `Names` implementations.

## The one place they agree today that would diverge under load

**The Rust chat driver's poll pause is not cancellable.** In the settle loop, `Driver.rs` awaits
`self.Pace.Sleep(Wait)` directly, where `Wait = Poll.min(Call.Remaining(..))`. TypeScript's
`pause()` races the same wait against the caller's signal and resolves the moment the signal fires.

Today the two agree, because the loop re-reads on the next iteration and the next read starts with
`Call.Cancelled()` - which is why `generated/chat-answer-cancel` passes on both sides. The
difference is _when_ the caller hears about it. With the default `pollMs` of 250ms, a TypeScript
caller that cancels mid-answer is released immediately, and a Rust caller waits out the remainder of
the current poll interval. Under load - many sessions sharing one process, a page that has stopped
answering, a signal that fires while a slow read is in flight - that is up to a quarter of a second
per call of indistinguishable extra latency, and it lands exactly when the caller is trying to shed
work. Worse, the guarantee is not local: it holds only because the _pace_ eventually resolves. A
`Pace` whose `Sleep` never resolves - a stalled executor, a test with a virtual clock that does not
advance - turns a cancelled `ask` into a call that never returns, while the TypeScript driver
returns at once.

The fix is one combinator: `Race(self.Pace.Sleep(Wait), Call.Cancellation.Cancelled())`, which is
the same shape `Bound` already uses for the read itself. It is not applied here because it is a
change to the port's implementation, and this card owns the scenarios, not the port.

# Reflection and Coherence

How a system that can rewrite its own capability definitions stays honest about what it is running.
The formal apparatus is worth using only up to a point; this note says where that point is.

## The property worth naming

**Decision: this repository** - the term, the definition and the three things a safety claim may
name. No capture uses "manifest-enforcement coherence". The observation-boundary half of the third
item is the subject of `.hermes/research/research-575cb198.md`, which argues what an observation
must name and record; no section here draws on it yet.

**Manifest-enforcement coherence:** the capability manifest a runtime reports is the manifest it
actually enforces.

Not "the manifest is correct" - correctness is a separate, unprovable-in-general claim. Coherence is
checkable: read what the system says it is, then exercise the system and compare. Every safety claim
in this workspace should name one of three things: a state invariant, an observation boundary, or an
equivalence theorem. A claim that names none of them is prose.

## The trust boundary comes first

**Decision: this repository** - the argument that a self-check has no independent basis, and the
choice of the composition root plus the process that launches it as the party outside the mutation
authority. **Source:** `.hermes/research/rust-4ffde6d5.md` §3 for the mechanism the section relies
on: a source descriptor embedded in the crate and an external release descriptor binding it to the
delivered bytes, so a manifest read from the mutable store is not the only copy that exists.

If the mutation path can rewrite the reporter, the enforcer and the verifier, an internal self-check
has no independent basis for detecting coordinated deception - it is checking the story against
itself.

So one component must sit **outside** the mutation authority, and something external must attest to
its identity. In this system that is the composition root plus the process that launches it: the
root holds the manifest it bound, and the runtime can only report what it was given. A manifest read
from the mutable store alone is not evidence.

## The obligation, reduced to induction

**Decision: this repository** - the induction shape, the four-part mutation obligation
(authorisation, validation, migration, publication) and the transition table as the cheap version
that is still honest. No capture states any of them.

Coherence is an invariant, so the proof shape is an induction over transitions:

- establish `Inv(s0)` - the manifest bound at start-up is the manifest enforced at start-up;
- show `Inv(s) ∧ s →ℓ s' ⇒ Inv(s')` for every state-changing transition: admission, invocation,
  mutation, recovery, lease reuse, revocation.

For a mutation specifically, four things must jointly establish the invariant for the new
generation: authorisation, validation, migration, publication. If any one of them is missing, the
new generation is coherent only by accident.

Tests check instances of this; a general claim needs a proof or exhaustive checking of a finite
model. The cheap version that is still honest: a transition table listing every state-changing
operation beside the invariant it must preserve, and a conformance run per generation.

## Where the apparatus collapses

**Decision: this repository** - the boundary at declarative records under a fixed interpreter, and
the reduction to ordinary versioning. No capture discusses reflection; this is why
`research-575cb198.md` cannot be read as the source of this section despite the name the brief gave
it.

If reflection only reads and replaces **declarative records under a fixed interpreter** - which is
what this workspace is - then none of the higher-order machinery is needed. The requirement is
ordinary versioning:

- a versioned contract,
- a validator,
- a compiler or installer,
- a migration `m: Vn → Vn+1`,
- and a test that the migration composed with enforcement preserves the contract.

No reflective tower is required merely because the records describe executable capabilities. The
check is: demonstrate that every admitted record is interpreted by the same trusted semantics.

## Where it stops being ordinary migration

**Decision: this repository** - the three changes that defeat record validation (interpreter,
authorisation semantics, the manifest language itself), and the "new policy approved versus old
policy preserved" distinction.

If an authorised update can change the **interpreter**, the **authorisation semantics**, or the
**meaning of the manifest language**, record-shape validation is not enough. Then you need either a
semantics-preservation or refinement obligation between interpreter versions, or an explicit
declaration that the policy changed.

The distinction to enforce in every upgrade: _new policy approved_ versus _old policy preserved_.
Conflating them is how a rewrite gets described as a refactor.

## What gets built

**Decision: this repository** - all four items. Nothing in the captures proposes a `reflect`
operation, a generation-scoped conformance run, a transition table or the semantics-change refusal.

1. A `reflect` operation that returns the enforced manifest **and its generation id**, answered from
   the composition root rather than from the mutable store.
2. A generation-scoped conformance run: the contract test suite executes against the generation, and
   its result is recorded with that id.
3. A transition table in the runtime package listing each state-changing operation beside the
   invariant it preserves.
4. A refusal: a mutation that would change interpreter semantics is rejected unless the caller
   states which policy changed, so the audit trail records the difference between preservation and
   replacement.

Bisimulation is used where it belongs - comparing executions across two implementations of the same
port, or across two interpreter versions. Congruence is the obligation when claiming those
comparisons survive inspection and mutation contexts. Neither is needed to say "this generation
enforces what it reports".

**Source:** `.hermes/research/rust-4ffde6d5.md` §2 - the acceptance suite the capture requires
before the TypeScript sidecar is removed (attach/launch, navigation races, evaluation timeout,
disconnect, disposal, shared-browser ownership) is one such comparison, named concretely rather than
gestured at. **Decision: this repository** - the bisimulation and congruence framing, and the claim
that neither is needed for enforcement coherence.

## Thread 1 - hidden properties and disclosure

**Source:** [`research-575cb198.md`](../.hermes/research/research-575cb198.md), 154 lines.

**Asked:** (1) is SpacetimeDB's execution model reactor-style, and what is actually documented about
concurrency and ordering; (2) what formal frame fits capabilities whose properties are hidden at
first and revealed by traces or by other actors - POMDP, epistemic logic, hidden Markov model - and
what Netrunner teaches about disclosure that is fair, legible and not degenerate; (3) how to
represent those properties in a relational database whose subscriptions push rows to clients without
leaking through the subscription itself, with the table design, the reducer rule, and where the leak
is unavoidable.

**Settled** (`:11-142`):

- Each database is a single-threaded actor: transactions in one database execute serially, different
  databases concurrently. "Reactor" is not the documented word; the architecture article says
  "actor" (`:11`, `:17`).
- Transaction guarantees are not scheduling guarantees. There is no global FIFO across clients and
  no guaranteed dispatch order for overdue scheduled reducers, so ordering has to be made explicit
  with sequence or version preconditions (`:14`).
- An action-conditioned POMDP is the frame for discovery, with an epistemic MDP as the close special
  case when properties are fixed; the belief update is Bayesian filtering, and a stored confidence
  number is not a calibrated model (`:21`, `:24`, `:112`).
- Epistemic logic answers a different question - what each actor knows, and what they know about
  others' knowledge - and probabilities are degrees of belief rather than knowledge (`:115`).
- Latent truth, authorised evidence and actor belief are three records with three authorities;
  another actor's statement is testimony, not a mutation of truth (`:118`).
- Netrunner's lesson is rule-governed access, not face-down storage: every reveal must name the rule
  authorising its target, audience and extent, repeated probing must be bounded, a persistent
  property must not be rerolled on inspection, and "hidden again" is not "unknown again" (`:119`,
  `:122`, `:123`).
- Never publish a secret-bearing row and conceal it client-side: subscriptions synchronise
  authorised rows into the client cache, private tables are inaccessible, and a caller-aware view
  can project by `ctx.sender` (`:127`, `:132`).
- A schema (`CapabilityPublic` / `CapabilitySecret` / `Observation`), an `observe(target, action)`
  reducer that charges and reveals in one transaction, recorded disclosure preferred over a live
  join to current truth, traces treated as a subscription surface, and a nonleakage target stated as
  observable- transcript equality rather than equal visible values (`:131-141`).

**Left open:** the five follow-ups the thread lists (`:145-149`) - rollback, cross-module
concurrency, scheduled-reducer sequencing, subscription guarantees, replication determinism - plus
the checks embedded in its findings (dominance, racing probes, canary, paired worlds). All eight are
`Documentation/Open-Questions.md` Q1-Q8.

# Review of the first pass

An external review of the whole corpus - five batches, 111 files - was asked for after the Rust port
landed. This records its verdict and the defect it found, because the verdict is not a list of nits.

## The finding, in its own words

> The central problem is **authority**: the documents specify one coherent authority over admission,
> leases, generations and effects, but the code implements several disconnected approximations. The
> CLI can run browser operations without the lease engine; the lease engine authorizes an arbitrary
> future rather than fencing the destination; and the database-as-authority design has no
> corresponding implementation in the supplied Rust sources. These are not small omissions around an
> otherwise implemented contract. They are different architectures.

Three separate claims, each checkable:

1. **The CLI can bypass the lease engine.** A browser operation reachable from the composition root
   without going through admission is an effect with no authority behind it.
2. **`WithLease` fences the caller, not the destination.** The counterexample it gave:

    ```
    lease is live
    WithLease admits the callback
    callback waits
    lease expires
    callback performs the external write
    WithLease returns success
    ```

    The in-flight counter stops a second local claimant from taking over during that callback. It
    does not stop the old callback writing after expiry.

3. **The database-as-authority design has no implementation.** `Documentation/Observability.md` says
   a reducer is where a transition happens; the Rust sources contain no reducer call on that path,
   so the authority is described and not built.

## Why the existing test does not catch it

`a_claim_during_an_effect_on_an_expired_lease_is_refused` blocks takeover until the future settles
or is dropped. That substitutes "wait for the old effect" for the specification's "revoke authority
despite a physically live worker" - the test agrees with the implementation rather than with the
requirement.

And dropping the future decrements the in-flight count, while dropping a Rust future does not prove
the browser-side operation stopped. The count therefore measures unsettled local futures, not
unsettled external effects.

## The revision it proposes

Stop presenting arbitrary callback admission as fencing. An effect should carry its lease and
generation identifiers and be **checked by the destination** - the reducer that records it - rather
than trusted because a wrapper admitted it earlier. That is the same conclusion
`Documentation/Reflection.md` reached for schema generations, applied to effects: the check belongs
where the write lands.

## What this changes about the plan

The port is not finished; it is a second architecture that agrees with the first only in vocabulary.
The next card is not "more crates" but "one authority": admission, lease and generation checked at
the point of effect, with a test that fails when the check is moved back into the caller.

# Scope, and the parity with TimeLine

Agentic is not TimeLine's toolkit. It is a local agent and swarm: it gathers links, browses,
researches, and organises that work in SpacetimeDB. TimeLine is a product - an archive, a site, a
decision corpus and the tooling that maintains them.

They share a vocabulary (capabilities, ports, leases, evidence) and one direction of travel:
**research done here can be fed into the DELO project as findings.** Nothing travels the other way,
and nothing here is required for TimeLine to build.

## What Agentic is

| Capability            | What it does                                                             | State class     |
| --------------------- | ------------------------------------------------------------------------ | --------------- |
| `browser-cdp`         | attach to or launch a browser, evaluate in a page, dispose               | holds-transport |
| `chat-driver`         | ask a chat product, verify mode and model, read the answer and its trace | holds-transport |
| `design-verification` | measure a built page and produce evidence, with no design baked in       | stateless       |
| `skill-contract`      | discover, validate and digest a corpus of skill documents                | stateless       |
| `runtime`             | admission, leases with a fence, per-run budgets, cleanup                 | holds-workspace |
| `spacetime-catalog`   | the database rules: capabilities, generations, leases, probes, trace     | stateless       |

## What TimeLine is

| Surface          | What it does                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------- |
| the archive      | posts, authors, observations, media, membership - written only through `observe`          |
| the site         | a prerendered Astro surface that reads the archive and never scrapes                      |
| the RFC corpus   | 76 decision records, their frontmatter contract and the issue board that publishes them   |
| design verifiers | three probes that measure the built workspace, showcase and spread against a written spec |
| the tool layer   | 125 TypeScript modules: CLI, transport, store, model, command                             |
| the gates        | `pnpm run check`: RFC frontmatter, skills, compatibility, state, tokens, position, tests  |

## Parity: what one has that the other does not

| Concern                           | Agentic                                                            | TimeLine                                     |
| --------------------------------- | ------------------------------------------------------------------ | -------------------------------------------- |
| A browser session                 | yes - attach or launch, with ownership recorded                    | yes, but only to verify its own pages        |
| Asking a chat product             | yes - mode and model verified, trace captured                      | no                                           |
| Research corpus                   | yes - threads captured as records with frontmatter and a catalogue | no                                           |
| A published site                  | no                                                                 | yes                                          |
| An archive of records             | no                                                                 | yes                                          |
| A decision corpus with a contract | no                                                                 | yes - 76 records, gated                      |
| Issue-board synchronisation       | no                                                                 | yes - `rfc_board.py`, read-only by default   |
| Leases and admission              | yes - the runtime's whole purpose                                  | no                                           |
| Design measurement                | yes - the engine, with no design in it                             | yes - the engine plus the site's own numbers |
| Skill validation                  | yes - generic corpus rules                                         | yes - its own 13 skills and their contract   |
| Persistence                       | SpacetimeDB, as the scheduler and the record                       | files plus SpacetimeDB for the live view     |

## The one direction of travel

A research finding from Agentic becomes a card in the DELO board, and the card is written in
TimeLine's terms: a file, a claim, a command that settles it. That is the whole interface. Agentic
does not import TimeLine's code, does not read its database, and is not a dependency of its build.

## What this rules out

- Agentic does not grow a copy of the site, the archive or the RFC board.
- TimeLine does not grow a copy of the runtime, the chat driver or the research corpus.
- A capability that both need - measurement, skill validation - lives in Agentic as the engine and
  in TimeLine as the site's own expectations, which is why the two versions of `design-verification`
  are not duplicates.

# Bounded Sequences

A sequence of page operations is a sequence of budgets, not a script with sleeps in it. Each step is
one `Call`: a deadline, a cancellation, and a result that is classified before the next step runs.

---

## One budget per step, and stop on the first refusal

```sh
Target/debug/agentic browse --attach <ws> --bind <target-id> \
  --expression '<step 1>' --timeout 20000
Target/debug/agentic browse --attach <ws> --bind <target-id> \
  --expression '<step 2>' --timeout 20000
```

Two rules make a sequence trustworthy:

- **A failed step ends the sequence.** A step whose result is `null`, `false` or an error is a
  refusal, not a no-op, and the next step's premise has just become a guess.
- **The budget belongs to the step, not the run.** One long deadline shared by ten steps hides which
  step spent it; ten short ones name the step that hung.

Between steps, re-read the state the next step depends on. A page that re-rendered between two
evaluations can leave the second expression pointing at an element that no longer exists, and the
failure then looks like a bad selector rather than a stale handle.

---

## A batch mutation is verified by the server, not by the click

A click that returns `true` proves the element was there and was clicked. It does not prove the
action happened. Verify each mutation by a scalar the server owns - a count, a state field, a row
that is now absent - and record it beside the input:

```
item=<id> clicked=true after=<state> ok=true
```

A batch that reports "12 of 12 clicked" and no state has reported nothing. The audit line is the
deliverable; the clicks are how it was produced.

Prefer an idempotent form where the product offers one (set-to-value over increment), because a
batch interrupted halfway is then re-runnable.

---

## A paginated read ends on a repeated key, not on a page count

Collect until the page yields an identity you have already seen, and cap the walk independently of
that. A count is a guess about a page that may add rows while you read it; a repeated id is evidence
that you have come back around.

Deduplicate on a stable id, never on position: a virtualised list re-renders rows and a positional
key renames them mid-read.

---

## A wait that settles before anything changed has not seen the change

"The value stopped changing" is true the instant the wait begins on a page that has not started
changing yet. A watcher must observe at least one change since it began before "stable" is allowed
to mean "finished", and the deadline stays the only other exit.

The symptom is a step that finishes in one poll with the old value while the new one lands seconds
later. For a chat product the same rule is why `busy` is read before stability is counted.

## Claim → test

| Claim                                 | Test                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| A sequence stops on the first refusal | make step 2 return `false`; step 3 is never sent                                                        |
| A budget names the step that hung     | give one step `--timeout 2000` against a page that never answers; the error names that step's operation |
| A batch mutation is verified          | after the run, the audit line's `after=` value matches a fresh read of the same state                   |

| A stale handle is reported as such    | remove the target element between two steps; the second step fails instead of reporting success         |
