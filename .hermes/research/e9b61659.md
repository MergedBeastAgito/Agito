## Post identity is stable, but article position is not

The selector explicitly acknowledges that the page recycles articles as you scroll; it provides ID-based lookup for that reason (`Maintain/Source/Browser/Selector/Post.ts:8–10, 94–96`). Initial resolution by `--id` uses that protection: `withTarget()` passes the requested ID into `snapshot()` (`Maintain/Source/Transport/CDP/Post.ts:63–64, 137`).

But the first mutation does not preserve that identity. `toggle()` sends only the article index and control, and `settle()` also polls by index. The selector chooses by ID only when the request includes one; otherwise it selects the current article at that index (`Maintain/Source/Browser/Session/Post.ts:112–136`; `Maintain/Source/Browser/Selector/Post.ts:204–205`).

The inference is a time-of-check/time-of-use failure: if article A occupied index 0 during the initial read, but article B occupies it when the click executes, the click can affect B. The returned post identity still comes from the original context, A (`Maintain/Source/Transport/CDP/Post.ts:196–203`).

This can be silent. The code checks that an article and button were found, not that the clicked article has the original ID. A later read by A’s ID does not undo the click on B.

To settle this, I would exercise the exported selector expression against a controlled page: snapshot A, reorder or replace the articles before the toggle expression, then record which button receives the click. This needs no live-account mutation.

## A URL is treated as a locator, not an identity constraint

For `--url`, validation merely checks whether `idFromHref()` finds `/status/<digits>` anywhere in the string. It does not validate the URL’s host or scheme (`Maintain/Source/Model/Post/Post.ts:24–26`; `Maintain/Source/Transport/CDP/Post.ts:69–74`).

More importantly, `wanted` is populated only for the `id` target variant. A URL target therefore waits for any article and snapshots index 0, rather than selecting the ID embedded in the URL (`Maintain/Source/Transport/CDP/Post.ts:63–64, 116–137`).

What I am reading: there is no requested-ID check on the URL path through `withTarget()`.

What I am inferring: a redirect, an unexpected page layout, or a thread where another article appears first can produce a successful reading of another post. The same path is used for like/bookmark operations, so the assumption matters beyond extraction. Whether the current X detail page actually presents that ordering requires a run.

I would test a controlled URL containing `/status/123` whose page contains articles 999 and 123 in that order. The expected invariant is that the resolved post is 123, regardless of article order.

## “An article exists” is treated as “the post is ready”

`withTarget()` waits up to 25 seconds for `document.querySelectorAll("article").length > 0`. Absence produces a named `no-post` failure; presence proceeds directly to the snapshot (`Maintain/Source/Transport/CDP/Post.ts:116–150`).

That proves the existence of an article, not that its text, author, controls, or media have finished rendering. The selector supplies empty text, an empty author handle, null time, and empty media when the corresponding nodes are absent (`Maintain/Source/Browser/Selector/Post.ts:104–138`).

Consequently:

- No articles is loud: `no-post`.
- A partially rendered article can be silent: a structurally successful reading with missing fields.
- With an ID target, an unrelated article can satisfy readiness before the desired post arrives; the immediate ID snapshot can then fail loudly even though the desired post would appear later.

The last case is an inference about asynchronous rendering, not an observed live-page failure. I would run a fixture that inserts an unrelated article immediately, the target article later, and its media later still; then compare when the transport returns with when the fixture becomes complete.

## Extraction assumes the DOM preserves specific meanings

The reading depends on relative permalinks matching `/handle/status/digits`, specific `data-testid` values, and English metric keywords. These are not merely cosmetic selectors: they determine identity, control state, and numeric values (`Maintain/Source/Browser/Selector/Post.ts:55–79, 83–90, 104–123, 140–157, 208–235`).

Some consequences are directly visible:

- Unreadable counts become zero rather than unknown.
- Missing controls have `present: false` and `active: false`.
- Missing text becomes `""`.
- A video without `src` can be represented using its poster URL while retaining `kind: "video"`.

Those behaviors are implemented at `Maintain/Source/Browser/Selector/Post.ts:55–65, 119–132, 208–235`.

The inference is that a selector change, localized count format, or delayed rendering can turn “not observed” into apparently valid data. For example, parsing removes commas before interpreting the number, so a decimal-comma label can be misread; the views selector also specifically searches English “Views”/“views” (`Maintain/Source/Browser/Selector/Post.ts:58, 143`).

These are predominantly silent failures. I would evaluate the actual exported `expression()` against DOM fixtures with missing controls, localized labels, absolute rather than relative permalinks, and video posters without playable sources. The test should distinguish unknown from zero/false/empty, rather than merely assert that extraction returns an object.

## Background visibility is handled asymmetrically

There is a deliberate workaround for lazy media: `reveal()` enables focus emulation and an active lifecycle state. But it is called only when the target was addressed by ID and the tool opened a temporary tab (`Maintain/Source/Transport/CDP/Post.ts:33–45, 63–64, 129–135`).

A URL target can also open a temporary tab, but does not take that branch. An ID target that reuses an already-open background tab does not take it either (`Maintain/Source/Transport/CDP/Post.ts:82–85, 97–111`).

The source itself explains that hidden detail tabs can otherwise report empty media. What remains an inference is how often current browser/page behavior exposes this discrepancy. In addition, both reveal commands swallow errors, so a failed workaround has no warning (`Maintain/Source/Transport/CDP/Post.ts:38–44`).

I would compare the same photo post through `read({id})` and `read({url})`, first with no existing detail tab and then with a pre-existing background tab. That would establish whether the representations diverge in the current environment.

## “Network idle” means no recent event—not no outstanding request

The session updates one timestamp on request start, finish, or failure. `waitForIdle()` returns true once that timestamp has been quiet long enough; it does not maintain a set of in-flight requests (`Maintain/Source/Browser/Session/Session.ts:75–90, 139–147`).

Therefore a request can start, remain pending longer than the quiet interval, and still satisfy this implementation’s idle condition. That follows from the algorithm; it does not require speculation about X.

The practical consequence is inferred: a reload or tab close can occur while a mutation request remains outstanding. If the Network domain is unavailable, the session silently degrades further to a timed quiet window (`Maintain/Source/Browser/Session/Session.ts:81–89`).

I would attach to a local fixture that starts a fetch whose server response is deliberately held open, then measure `waitForIdle({quiet: 600})`. If it resolves while the request remains pending, it proves the semantic gap.

## A completed click is not consistently a verified write

The mutation path contains useful safeguards: no click if the observed state already matches, named failures for missing article/button, and reload-based verification for temporary tabs (`Maintain/Source/Browser/Session/Post.ts:112–133, 64–97`).

But it also contains several weaker assumptions:

- The result of the six-second `settle()` is discarded.
- If the post/control cannot be read afterward, `now` defaults to the desired state.
- Reload-based verification can return null; that leaves the earlier value in place.
- Existing user tabs are not reloaded for persistence verification.

These behaviors are explicit in `Maintain/Source/Browser/Session/Post.ts:135–146`; the persistence fallback is at `:69–97`.

Thus `now: true` need not mean “the server accepted and retained the change.” In the missing-control branch it can mean “the caller wanted true and verification no longer had a readable control.”

A server rejection that remains visible as the opposite state can be returned as `now != want`, which is observable but not thrown as an error. A rejection masked by optimistic state or missing verification can be silent at the transport boundary. I have not traced the CLI’s treatment of that returned mismatch in this pass.

I would test `toggle()` with a fake Session that reports a successful click, never settles, and then loses the control. A second test would make the temporary-tab reload fail. Neither requires clicking a real account.

## CDP failures are usually loud; polling deliberately blurs their cause

The underlying client rejects protocol errors, times out individual commands, and rejects pending calls when the socket closes. Those become `cdp-error` or `cdp-unreachable`, rather than indefinite pending operations (`Maintain/Source/Browser/CDP/Client.ts:107–136, 139–179`).

Page evaluation also turns JavaScript exceptions into named `cdp-error` failures (`Maintain/Source/Browser/CDP/Command/Evaluate.ts:30–42`).

However, `Session.waitFor()` catches every evaluation error and keeps polling—not only the transient execution-context destruction mentioned in its comment (`Maintain/Source/Browser/Session/Session.ts:149–163`).

That is a reasonable navigation-recovery strategy with a diagnostic cost: a permanently invalid expression or dead connection can emerge as a generic readiness timeout instead of its original cause. In the post path this becomes “the page showed no posts”; other direct evaluations remain loud.

I would inject a permanent evaluation error and compare it with a transient context-destruction error. The important assertion is not just that both terminate, but whether the permanent error’s cause remains available to the caller.

## Cleanup assumes attachment succeeded and close failures are harmless

`withTarget()` encloses attachment in its `try/finally`, so it attempts to close a temporary tab even if attachment fails (`Maintain/Source/Transport/CDP/Post.ts:68, 115, 162–172`).

`withPage()` attaches before entering its cleanup `try`. If it has opened a tab and attachment rejects, that cleanup block is never reached (`Maintain/Source/Browser/Session/Page.ts:57–85, 113–123`).

That is a source-confirmed cleanup gap. Its practical manifestation would be a leaked tab after an attachment failure. Both cleanup paths also suppress close errors on the assumption that the tab is already gone; an unreachable browser is another possible explanation, so cleanup failure can be silent.

I would inject an attachment failure after successful tab creation and assert that the close operation is attempted. This should be a controlled test, not a run that deliberately leaves tabs in your browser.

## The architectural distinction to preserve

The transport correctly separates “live browser” from “shadow archive”: the view transport refuses browser operations and mutations, and requires an ID for archived reads (`Maintain/Source/Transport/View/Transport.ts:59–95`). Transport selection also rejects unsupported declared requirements before command execution (`Maintain/Source/Transport/Select.ts:47–58`).

The weakness is not that the subsystem lacks failures. It is that its strongest failure signals concern connection and element availability, while its weakest signals concern the meaning of a successful result. The most valuable tests would therefore adversarially change identity, delay completeness, and reject persistence—not just disconnect CDP.
