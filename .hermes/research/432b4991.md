I need a single state chart for a system I have been designing across several sessions, and I want it to reconcile the domains rather than draw four separate diagrams.

The system: an agentic capability layer, written in Rust, where capabilities (browser control over CDP, chat research, design verification, skill validation) are leased by a runtime, carry hidden properties that other actors can probe, and run against a SpacetimeDB database whose schema is self-describing and whose generations must stay coherent with what is enforced.

Reconcile these five domains into one chart:

1. EXECUTION LIFECYCLE. prepare reusable infrastructure -> lease an isolated context -> bind identity and task -> validate credentials, connections and versions -> execute within a fresh budget -> persist only authorised artefacts -> destroy or prove a reset. State classes decide what may be pre-warmed: stateless, holds-transport, holds-identity, holds-workspace.
2. DISCLOSURE. A private property is hidden; an actor probes it; the probe charges a cost and writes an audience-scoped immutable observation tied to a property version; beliefs are derived and disposable. Before an authorised reveal, two worlds differing only in the protected property must produce the same observable transcript for an unauthorised actor.
3. TIME. Four timestamps - event, ingest, scheduled, run - with three lags between them, each a difference across clock authorities, stored signed. Intervals do not yield an occurrence; one-shot rows do.
4. SCHEMA GENERATIONS. A capability manifest is bound by a composition root; the runtime may only report what it was bound with; a mutation must jointly establish authorisation, validation, migration and publication for the new generation; an update that changes the interpreter or the manifest language must declare "policy changed" rather than claim preservation.
5. FAILURE AND RECOVERY. A lease expires while its worker still runs (the fence must refuse the late write). A warm transport is open but dead. A probe races a one-use allowance. A schema generation is published while a lease is live.

`DISC` represents one property-version/probe interaction; `TIME` represents one occurrence and its attempts; `GEN` represents a generation lineage. These are parameterised state families, not singleton global objects. Multiple leases and probes instantiate the same chart.

The generation region deliberately leaves the predecessor active during candidate preparation. Its state names describe the publication operation, not permission to expose a half-migrated database.

## Shared guards and invariants

## Effect admission is the reconciliation point

For every durable write, disclosure, allowance consumption, and externally mediated effect, evaluate at the authoritative boundary:

$$\begin{aligned}
\operatorname{admit}(x) ={}&
\operatorname{leaseLive}(x.\ell,\operatorname{authorityNow})\\
&\land x.f=\operatorname{currentFence}(x.\operatorname{scope})\\
&\land \operatorname{generationAdmitted}(x.g,x.\operatorname{operation})\\
&\land \operatorname{bindingMatches}(x.\operatorname{identity},x.\operatorname{task})\\
&\land \operatorname{authorisedNow}(x)\\
&\land \operatorname{budgetAdmitted}(x)\\
&\land \operatorname{expectedVersionsMatch}(x).
\end{aligned}$$

The version checks are operation-specific: property version for a probe, object version for a conditional update, and schema/interpreter identity for generation-sensitive operations.

Check and mutate in one serialised transaction or equivalent conditional operation. Do not check, return to the worker, and later trust the result.

A monotonically increasing fence alone does not prove that a lease remains live: an expired worker can arrive before any newer token has reached the destination. Your requirement therefore needs authoritative expiry/revocation checking as well as fence enforcement, or an equivalent atomic invalidation mechanism. Resource-side fencing is necessary; “highest token seen” alone is insufficient for immediate expiry rejection.atlasofengineering+1

## A generation is more than a schema number

Use a generation identity that commits to at least:

```
generation_id
schema_digest
manifest_digest
interpreter_digest
policy_digest
migration_provenance
composition_root_binding
```

A runtime reports its immutable binding, not whatever generation the publication registry currently calls “latest.” Store the generation attached to each effect so the enforced interpretation remains auditable.

## Time is evidence, not lease authority

For a fully populated occurrence:

$$L_{EI}=t_{\mathrm{ingest}}-t_{\mathrm{event}},\qquad
L_{IS}=t_{\mathrm{scheduled}}-t_{\mathrm{ingest}},\qquad
L_{SR}=t_{\mathrm{run}}-t_{\mathrm{scheduled}}.$$

Store signed differences and the authority/clock-domain identifiers for both operands. Preserve negative values; do not silently clamp them or infer causal impossibility from them. Before run admission, $t_{\mathrm{run}}$ and $L_{SR}$ are absent, not zero.

These fields must not determine lease validity. Lease validity uses its designated authority; local budget timing uses a suitable monotonic clock. Define $t_{\mathrm{run}}$ as authoritative start admission, unless you explicitly need a separately evidenced worker-start timestamp.

## Where the domains disagree—and the resolution

## 1. “Hidden” versus “successfully probed”

An observation can reveal a property even if no UI labels it a reveal. Therefore `X_DISCLOSE`, not some later presentation action, is the declassification boundary.

A paid probe is not automatically an authorised probe. An actor lacking reveal authority must receive the same observable transcript in the two protected-property worlds—including permitted observations of errors, charges, timing, retries, termination and output size. Timing and termination are recognised information-flow channels, not merely implementation details.arxiv+1

Resolve this by making each probe contract specify the actor, audience, property version, permitted information function and disclosure point. Everything before that point must be secret-independent within the stated threat model.

## 2. “Expired” versus “still running”

Execution state and authority state are different coordinates. Expiry does not prove termination; cancellation does not prove revocation.

Resolve this with `EXEC_AuthorityLost`: revoke admission first, then stop or isolate the worker. Do not wait for cooperative cancellation to protect data. Where an external endpoint cannot enforce fencing or equivalent authority checks, put an enforcing adapter in front of it—or explicitly exclude that endpoint from the strong guarantee.atlasofengineering+1

## 3. “Warm” versus “safe to reuse”

Warmth describes retained substrate; safety describes retained state and authority.

| State class | Permitted warm substrate |
| --- | --- |
| `stateless` | Code, immutable configuration and non-sensitive caches. |
| `holds-transport` | Transport only after bounded health/protocol checks; prove it carries no inherited identity or session authority. |
| `holds-identity` | Identity-bearing resources only inside an explicit principal-scoped pool; never treat them as anonymous infrastructure. |
| `holds-workspace` | Workspace only within an explicit tenant/task scope, or after a verified reset to a declared baseline. |

Treat these as cumulative retention hazards, not necessarily an exclusive enum: a browser context can hold transport, identity and workspace simultaneously. If an enum is required, apply the strongest contract plus retained-resource metadata.

## 4. “Published” versus “what this live lease enforces”

A registry publishing $g+1$ cannot transform a $g$-bound runtime into a $g+1$ runtime.

Choose one explicit publication mode:

- Retain compatible leases: old enforcement and data interpretation remain available and addressable for $g$.
- Revoke incompatible leases: activation invalidates them, and their next effect fails admission.
- Drain before cutover: block new leases, finish or revoke existing ones, then activate.

If two interpretations cannot safely coexist over the same mutable database, compatibility mode is unavailable. Pinning a manifest string alone does not solve that.

An interpreter or manifest-language change must produce a “policy changed” declaration. Behavioural equivalence tests may accompany that declaration; they do not justify relabelling it preservation.

## 5. “Atomic mutation” versus a long migration

Authorisation, validation, migration and publication need one jointly established outcome, not necessarily one long database transaction.

Resolve this with staged work plus an atomic activation boundary. If migration modifies the live predecessor’s data in ways it cannot interpret, staging is no longer isolated: enter controlled cutover and block incompatible access. A migration failure then requires recovery, not an unconditional “return to old.”

SpacetimeDB exposes module/schema introspection and migration-validation diagnostics, but those facilities do not themselves establish your composition-root and live-lease coherence contract. That remains an application-level invariant.[spacetimedb](https://spacetimedb.com/changelog/v2.11.0)

## 6. “Fresh budget” versus “fresh allowance”

Execution budget belongs to an attempt. A one-use disclosure allowance belongs to its declared actor/task/property scope.

A retry gets a new execution budget only under retry admission. It does not restore a consumed allowance, erase a charge or create a second occurrence. Persist the allowance ledger outside disposable worker state.

## 7. “Occurrence” versus “interval”

An interval specifies recurrence; it does not identify a particular execution. Materialise a one-shot row before claiming work. Use separate identifiers for schedule definition, occurrence, attempt and effect.

That separation makes missed ticks, catch-up, retries and duplicate delivery explicit instead of hiding them behind one overloaded “scheduled” state.

## States missing from the original lifecycle

The chart includes the most consequential omissions; these deserve explicit implementation states or substates:

1. Admission blocked / draining. Needed when publication must stop new leases without immediately destroying existing work.
2. Revoked but physically alive. Distinct from failed, stopped and expired; it is the essential stale-worker state.
3. Outcome unknown / reconciling. A lost acknowledgement cannot establish whether an effect committed. Resolve through durable effect IDs, receipts or inspection before replay.
4. Budget reserved / exhausted. Reservations prevent parallel actions from each independently passing the same remaining-budget check.
5. Disclosure reserved / aborted. Needed if probing requires costly external work before the final atomic observation commit. Specify reservation expiry and whether the allowance is held or spent.
6. Generation incompatible / recovery required. “Migration failed” is not equivalent to “predecessor is intact.”
7. Credential revoked / renewal pending. Connection liveness and credential validity can diverge after initial validation.
8. Reset unproven / quarantined. Cleanup returning successfully is not reset evidence; an unproved context never re-enters the pool.
9. Occurrence cancelled / skipped / dead-lettered. Not every one-shot reaches a run, and not every failed attempt should retry forever.
10. Evidence unavailable. If audit or provenance persistence is mandatory, inability to write it must block the protected effect rather than silently downgrade the guarantee.

The unifying boundary is admission to an effect: it is where lease authority, generation interpretation, budget, disclosure permission, property version and occurrence identity must agree. Physical resource states and derived beliefs can lag behind that boundary; authority cannot.
